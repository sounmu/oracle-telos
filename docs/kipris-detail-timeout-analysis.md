# KIPRIS 상세 조회 시간 초과 분석

작성일: 2026-10-17
상태: 코드 분석과 개선 제안. 아래 개선안은 아직 구현하지 않았다.
관련 목표: [해커톤 MVP](hackathon-mvp.md)

## 1. 발생 현상

검색 중 다음 안내가 표시된다.

> 요청 시간 제한으로 상세 20건 중 2건만 받았습니다.

이는 조회하려던 상세 20건 중 제한 시간 안에 완료된 결과가 2건이라는 뜻이다. 검색 결과 자체가 2건뿐이라는 의미는 아니다.

## 2. 코드에서 확인한 구조

관련 파일:

- `src/lib/korea/search.ts`: 실시간 검색의 시간 제한, 후보 선별, 상세 조회와 색인 저장.
- `src/lib/korea/kipris.ts`: 특허별 서지상세·CPC 조회와 상세 배치 처리.
- `src/lib/korea/http.ts`: 개별 외부 요청의 시간 제한.

현재 흐름은 다음과 같다.

`20초 타이머 시작 → KIPRIS 후보 검색 → 로컬 임베딩·관련도 선별 → 상세 조회 → 받은 결과 저장`

| 항목 | 확인한 동작 |
|---|---|
| 실시간 조회 제한 | `LIVE_TIMEOUT_MS = 20_000` |
| 타이머 시작 | 후보 검색 전에 시작하고 상세 조회에도 같은 중단 신호 전달 |
| 후보 선별 | 사용자 설명과 후보 제목·초록을 임베딩해 상세 조회 대상 선택 |
| 상세 처리 | `DETAIL_CONCURRENCY = 4`, 4건씩 배치 처리 |
| 특허별 완료 조건 | 서지상세와 CPC를 `Promise.all`로 함께 기다림 |
| 배치 완료 조건 | 현재 배치의 모든 요청이 끝나야 다음 배치 시작 |
| 개별 HTTP 제한 | 30초. 상위의 20초 중단 신호가 먼저 발생하면 먼저 중단 |
| 부분 결과 | 완료된 상세를 보존하고 색인에 병합 |
| 다음 검색 | 색인에 이미 있는 출원번호를 신규 상세 조회 대상에서 제외 |

20초는 전체 사용자 요청의 정확한 응답 시간 상한은 아니다. 임베딩과 저장 작업까지 같은 신호로 즉시 중단되는 것은 아니며, LLM 검색어 생성 등 바깥 단계의 시간도 별도로 존재한다.

## 3. 원인 해석과 아직 확인하지 못한 점

후보 검색과 임베딩에 걸린 시간만큼 상세 조회에 남는 시간이 줄어드는 구조다. 임베딩 모델의 첫 로딩이 길어지면 상세 조회를 시작할 때 이미 시간 예산을 많이 소모했을 수 있다.

특허별로 서지상세가 도착해도 CPC가 늦거나 실패하면 해당 특허의 상세 처리가 완료되지 않거나 실패한다. 또한 배치 안의 느린 요청 하나가 다음 배치 시작을 지연시킨다.

따라서 이번 메시지는 KIPRIS 조회의 시간 예산과 처리 구조에서 발생한 부분 완료 경고다. LLM 모델 변경만으로 해결되는 문제는 아니다.

다만 실제 요청의 단계별 시간 로그를 측정하지 않았으므로, 이번 실행에서 후보 검색·임베딩·서지상세·CPC 중 무엇이 가장 큰 지연 원인이었는지는 확정하지 않았다.

## 4. 해커톤용 우선 개선안

### 1순위: 첫 상세 조회를 상위 5건으로 제한

후보는 충분히 검색하고 제목·초록으로 관련도를 계산하되, 첫 응답을 위해 조회하는 상세는 상위 5건으로 줄인다. 나머지 후보의 상세는 사용자가 선택할 때 가져온다.

목표는 전체 후보 수를 무조건 줄이는 것이 아니라 비교에 필요한 상세를 먼저 확보하는 것이다. 미조회 후보를 결과 목록에 보여주려면 현재 상세 기반 결과 구성과 구분하는 처리가 필요하다.

### 2순위: 후보 검색과 상세 조회의 시간 예산 분리

후보 검색용 제한과 상세 조회용 제한을 분리한다. 상세 조회의 타이머는 실제 상세 요청을 시작할 때 생성해 앞선 임베딩 시간이 상세 예산을 소진하지 않게 한다.

사용자의 요청 취소 신호는 계속 전달한다. 단계별 시간을 분리하더라도 배포 환경의 전체 요청 제한과 사용자 대기 시간을 고려해야 한다. 구체적인 제한값은 측정 후 결정한다.

### 3순위: CPC 실패·지연을 상세 실패와 분리

초록·청구항 등 서지상세를 확보했다면 CPC가 없더라도 비교에 사용할 수 있게 한다. CPC 미확보 상태는 명시하고, 조회 실패를 실제 분류 정보 부재로 해석하지 않는다.

단순히 오류만 무시하면 CPC의 느린 응답을 계속 기다릴 수 있다. 별도 짧은 제한 또는 필요 시 조회 방식으로 지연도 분리해야 한다. 기존에 저장된 CPC가 있으면 실패한 재조회로 덮어쓰지 않는다.

### 후속 개선: 배치 대기 제거

동시 처리 수는 제한하되 한 특허의 처리가 끝나면 다음 특허를 바로 시작하는 작업 큐로 변경한다. 현재처럼 4건 모두가 끝날 때까지 다음 묶음을 기다리지 않게 한다.

동시 요청 수를 무조건 늘리기보다 이용 한도와 서버 응답을 확인하며 조절한다.

## 5. 임시 대응과 한계

- 같은 검색을 다시 실행하면 이미 저장된 특허를 제외한 나머지 후보의 상세를 조회할 수 있다.
- 부분 결과가 저장된 경우에만 이 이점이 있다. 반복 실행은 추가 API 호출을 발생시킨다.
- 20초를 60초로 늘리는 것만으로는 느린 단계와 배치 대기 문제가 해결되지 않는다. 사용자 대기 시간이 길어질 수 있다.

## 6. 검증 항목

- 후보 검색, 임베딩, 서지상세, CPC, 색인 저장의 소요 시간을 각각 측정한다. 인증키나 키가 포함된 요청 URL은 로그에 남기지 않는다.
- 캐시가 없는 첫 검색과 캐시가 있는 재검색을 구분해 확인한다.
- CPC가 늦거나 실패해도 확보한 서지상세로 비교할 수 있는지 확인한다.
- 일부 상세만 성공해도 해당 결과가 저장·표시되는지 확인한다.
- 후보 검색에 시간이 걸려도 상세 단계에 별도 예산이 주어지는지 확인한다.
- 사용자가 요청을 취소하면 불필요한 후속 API 호출을 중단하는지 확인한다.
- 나머지 후보를 클릭했을 때 상세 조회와 비교가 이어지는지 확인한다.
- 화면에서 후보 수, 상세 확보 수, 미조회·실패 상태를 구분한다.

권장 첫 변경 범위는 **상위 5건 우선 상세 조회 + 단계별 시간 제한 분리 + CPC 실패·지연 분리**다.
