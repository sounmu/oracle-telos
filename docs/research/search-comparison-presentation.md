# 검색 방식 비교 실험과 발표 대본

## 발표에서 전달할 결론

**임베딩 거리는 관련 후보를 찾는 데 사용하고, 그 후보가 왜 관련 있는지는 기술 요소와 원문을 대조해 설명한다.**

최종 서비스의 한국 검색은 토크나이저 + BM25와 임베딩을 RRF로 결합한다. 검색 방식 선택 UI는 만들지 않았다. 빠른 검색·에이전트가 공유하는 `rankResearch`에 적용했으며 선택적 법령·공시 검색에도 같은 어휘 검색을 사용한다. 미국 샘플 검색은 기존 임베딩 방식을 유지한다. 기술 요소 비교는 기존 서비스 기능을 유지하며, 비교 결과를 이용한 추가 순위 변경은 다섯 번째 실험 조건에서만 수행한다.

독립적인 정답 없는 이번 실험은 다섯 방식의 동작·순위·시간·근거를 비교한다. 정확도 우위나 전문가 판단과의 상관관계를 입증하는 실험은 아니다. 원문 인용이 존재하는 것과 그 인용에 대한 AI의 해석이 맞는 것도 서로 다르다.

## 45초 발표 대본

> 처음에는 특허 문서를 임베딩해서 가까운 특허를 보여줬습니다. 그런데 거리가 가깝다는 것만으로 어떤 기술이 겹치는지 설명하기는 어려웠습니다.
>
> 그래서 검색과 비교를 나눴습니다. 한국어 텍스트를 단어와 짧은 글자 묶음으로 나누고, 단어의 희소성과 문서 길이를 고려하는 BM25를 의미 검색과 결합했습니다. 이후 후보 특허의 원문에서 기술 요소가 겹치는지 비교하고, 근거 문구가 원문에 있는지도 코드로 확인합니다.
>
> 이 선택을 살펴보기 위해 같은 특허 목록과 같은 질문으로 임베딩, 기존 키워드, BM25, 임베딩과 BM25의 결합, 그리고 기술 요소 비교까지 추가한 다섯 방식을 자동 실행합니다. 결과에는 순위 변화뿐 아니라 어떤 기술 요소와 원문 때문에 순서가 달라졌는지 함께 남깁니다.
>
> 이번에 보여드리는 것은 점수 하나를 근거가 보이는 비교로 보완한 결과입니다. 독립 정답으로 검증한 정확도나 법적 위험 확률이라고 주장하지는 않습니다.

## 슬라이드 구성

### 1. 받은 질문

“임베딩 거리가 실제 기술적 관련성을 나타낸다고 볼 수 있는가?”

- 같은 주제의 문서는 가까울 수 있지만, 핵심 작동 방식은 다를 수 있다.
- 거리만 제시하면 어떤 부분이 겹치는지 사용자가 확인하기 어렵다.
- 따라서 후보 검색 점수와 원문 기반 기술 비교를 분리한다.

### 2. 채택 근거

| 근거 | 확인한 내용 | 우리 설계에 반영한 점 |
|---|---|---|
| [USPTO PE2E 공식 설명, 2쪽](https://www.uspto.gov/sites/default/files/documents/ai-sim-search.pdf) | 특허 텍스트·분류·인용·사람이 평가한 유사도를 모델 학습에 활용. 특정 문장·문단을 강조해 검색 가능 | 문서의 전체적인 유사성만으로 설명을 끝내지 않고, 구체적인 기술 내용까지 비교 |
| [PatentMind, ACL Findings 2026](https://aclanthology.org/2026.findings-acl.735/) | 기술 특징·적용 분야·청구 범위를 나눠 평가하고 전문가 주석과 비교 | 하나의 유사도 대신 기술 요소별 비교표 제공 |
| [DAPFAM, 2026](https://doi.org/10.1016/j.array.2026.100720) | 키워드·벡터·문단 검색·RRF 결합을 통제된 조건에서 비교 | 동일 후보 집합에서 다섯 조건을 비교하는 실험 |
| [Elasticsearch BM25 설명](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity) | 빈도 포화와 길이 보정, 기본 k1=1.2·b=0.75 | 동일 상수의 BM25 공식을 서버에서 계산 |

위 자료는 설계 선택의 참고 근거다. 해당 시스템의 구현을 재현했다거나, 논문 성능을 Telos에서 달성했다는 뜻이 아니다. 특히 한국어 성능은 별도 검증이 필요하다.

### 3. 실험 조건

| 방식 | 실제 구현 |
|---|---|
| 임베딩 단독 | 동일 색인의 청크 내적 점수 중 문서별 최댓값으로 정렬 |
| 기존 부분 문자열 | 변경 전 부분 문자열 일치 개수의 문서별 최댓값. 비교용 대조군 |
| BM25 단독 | 단어+한글 2/3글자 토큰에 BM25 적용. 청크별 점수의 문서별 최댓값 |
| 최종 하이브리드 | 운영 코드의 `rankResearch`를 그대로 호출. 의미·BM25 청크 순위를 RRF로 결합 |
| 하이브리드 + 기술 요소 비교 | 위 하이브리드 상위 N건에 `comparePatent`를 실행해 공통 요소/전체 요소 비율로 재정렬 |

공통 통제 조건:

- 한 번 읽은 한국 색인, 동일 청크, 동일 질의 임베딩, 동일 검색 계획을 사용한다.
- KIPRIS 추가 검색·수집 없이 고정 후보 내 정렬만 비교한다. 실시간 검색 전체의 회수율 실험은 아니다.
- 기본 세 질의는 반려동물 식단, 피부 고주파 제어, 배터리 과열 감지다. 대표 표본으로 간주하지 않는다.
- 검색 계획은 질의당 한 번 만들고 비교에도 재사용한다. 준비 시간은 검색 방식별 처리 시간과 구분한다.
- 비교 원문은 기존 함수와 같게 제목·초록·처음 최대 5개 청구항이며, 전체 권리 분석이 아니다.
- 모델과 색인 SHA-256, 원본 색인, 질의, 생성된 계획, 비교표를 저장한다. LLM의 다음 실행까지 동일 출력을 보장하지 않는다.
- BM25는 필터를 통과한 청크를 통계 단위로 삼는다. k1=1.2, b=0.75이며 재임베딩이나 색인 파일 형식 변경은 필요 없다. 청크 객체별 토큰 빈도를 메모리에 캐시하고 새 청크에는 새로 계산한다.
- 토크나이저 `ko-word-ngram-v1`은 NFKC·소문자 정규화 후 Node의 `Intl.Segmenter`로 단어를 나누고 연속 한글 2/3글자 토큰을 추가한다. 예: `혈당을`에 `혈당`이 포함된다. 조사 제거·품사 판별을 수행하는 형태소 분석기가 아니며, 짧은 글자 부분 일치로 잡음이 생길 수 있다. 질의와 청크에 동일 규칙을 사용한다. [단어 분할 API](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter)
- BM25와 토크나이저의 효과가 함께 바뀌므로, 이 실험으로 두 변경의 개별 효과를 분리해 주장하지 않는다. BM25 단독 실행이 토큰 캐시를 채우고 뒤의 하이브리드가 재사용하므로 순차 처리 시간을 공정한 속도 벤치마크로 해석하지 않는다.

재정렬 규칙:

1. 원문 인용이 확인된 공통 요소 수를 전체 질의 요소 수로 나눈다.
2. 미확인 요소를 분모에서 빼지 않는다. 일부만 확인돼 점수가 과장되는 것을 줄이기 위한 실험상의 선택이다.
3. 확인된 요소가 2개 미만이거나 비교 호출이 실패한 후보는 기존 자리에 둔다.
4. 나머지 자리에서만 점수 내림차순으로 재정렬한다. 동점이면 기존 순서를 유지한다.

이 규칙은 검증된 최적 계산식이 아니라 명시적인 실험 가설이다. 서비스의 ‘서늘/따뜻/뜨거움’ 계산식(공통/확인 요소)과 다르며 서비스 코드는 변경하지 않는다. JSON의 `score`는 기존 검색 점수, `elementScore`는 재정렬 가능한 후보의 기술 요소 비율이다.

### 4. 결과 화면에서 말할 내용

생성된 `report.md`의 질문별 순위표와 원문 인용을 보여준다.

> 같은 질문에 대해 다섯 방식의 상위 결과가 이렇게 나왔습니다. 마지막 방식에서는 이 특허의 [기술 요소]가 원문에 확인돼 순서가 [전 순위]에서 [후 순위]로 바뀌었습니다. 이 변경이 항상 더 정확하다고 단정하지 않고, 왜 결과가 나왔는지 근거를 확인할 수 있도록 했습니다.

순서가 안 바뀌었으면 그대로 말한다. ‘성능 향상’ 사례를 만들기 위해 질문이나 결과를 숨기지 않는다. 미확인이 많으면 비교 원문이나 후보가 충분하지 않았다는 관찰로 보고한다.

## 실행

```bash
# 입력 확인. OpenAI·KIPRIS 호출 없음
pnpm experiment:search --dry-run

# 기본 3질의 × 상위 5건. OpenAI 논리 호출 최대 18회, SDK 재시도 별도
pnpm experiment:search

# 한 질문으로 빠르게 확인
pnpm experiment:search --limit 1 --top 3

# 사용자 질의와 저장한 색인으로 재실행. 새 출력 폴더를 사용한다.
pnpm experiment:search --queries .cache/experiments/my-queries.json \
  --index .cache/experiments/previous/index.snapshot.json \
  --out .cache/experiments/new-run
```

`OPENAI_API_KEY`와 현재 임베딩 모델로 만든 로컬 한국 색인이 필요하다. `.env*`는 `@next/env`로 읽는다. 키가 없으면 오류로 중단하며 AI 비교를 흉내 내지 않는다. 임베딩 모델이 로컬에 없으면 모델 다운로드가 발생할 수 있다. BM25·토크나이저 자체는 추가 모델·API·패키지를 사용하지 않는다.

출력은 `.cache/experiments/`의 새로운 실행 폴더에만 저장한다. 기존 폴더를 덮어쓰지 않는다.

- `report.md`: 발표에서 확인할 순위·시간·기술 요소·인용문
- `results.json`: 전체 상위 N건, 계획, 비교표, 오류, 선택적 평가 지표
- `index.snapshot.json`: 사용한 비공개 색인 원본
- `queries.json`: 사용한 질의와 선택적 외부 정답

질의 하나가 끝날 때마다 보고서를 저장한다. 중단 시 완료 질의 수를 확인한다. 비교 호출 실패는 보고서에 남기고 종료 코드를 1로 반환한다. 실패 후보를 관련 없는 특허로 판정하지 않는다. 원문이 포함된 산출물은 Git이나 공개 정적 디렉터리에 올리지 않는다.

## 사람의 추가 채점 없이 평가하려면

이미 심사관 인용 등 외부 정답이 연결된 데이터를 확보하면 입력 질의에 `judgments`를 추가한다. 아래 ID는 형식 설명용이며 실제 데이터가 아니다.

```json
[
  {
    "id": "query-1",
    "idea": "평가할 기술 설명을 여기에 입력합니다",
    "judgments": {
      "source": "독립 평가 데이터의 이름·버전·출처 URL",
      "relevance": { "kipris:실제출원번호1": 3, "kipris:실제출원번호2": 0 }
    }
  }
]
```

라벨은 0~3 정수다. 이진 인용 정답이면 0/1로 넣는다. 관련 정답이 하나 이상 있고 반환 상위 3건이 모두 판정돼 있을 때만 nDCG@3와 Precision@3를 계산한다. Precision의 관련 기준은 라벨 > 0이다. 정답 ID가 후보 색인에 없으면 실행을 중단한다. 반환이 3건보다 적으면 Precision 분모는 3을 유지한다.

현재 스크립트가 공개 벤치마크를 자동 내려받거나 정답을 생성하는 것은 아니다. 같은 LLM이 생성한 기술 요소 점수를 그 방식의 정답으로 다시 사용하면 자기 평가가 되므로 그렇게 하지 않는다. 정답이 없는 기본 질의는 ‘미평가’로 표시한다. 이 경우 표는 설명 가능성과 동작 비교 자료로 사용한다.

## 예상 질문에 답하기

**“그래서 유사성과 상관관계가 입증됐나요?”**

> 아직 독립 정답으로 상관계수를 측정한 것은 아닙니다. 이번에는 거리만 제시하던 결과를 BM25와 원문 근거가 붙는 기술 요소 비교로 보완했고, 다섯 조건을 같은 데이터로 비교할 수 있게 만들었습니다.

**“왜 임베딩을 계속 쓰나요?”**

> 많은 후보를 빠르게 좁히는 역할이 필요합니다. 비용이 큰 기술 요소 비교는 상위 후보에만 적용하도록 역할을 나눴습니다. 실제 속도 차이는 보고서의 측정값으로 보여드립니다.

**“AI가 공통점이라고 하면 맞는 건가요?”**

> 인용문이 실제 원문에 있는지는 코드로 검증합니다. 다만 그 문장을 AI가 올바르게 해석했는지까지 보장하지는 않습니다. 그래서 원문 근거와 미확인 요소를 함께 보여줍니다.

**“기술 요소 비교 방식이 가장 좋나요?”**

> 근거를 확인할 수 있는 비교를 추가한 버전입니다. 정확도까지 가장 좋다고 말하려면 독립 정답에서 검증해야 합니다. 비용과 처리 시간도 같이 비교하고 있습니다.
